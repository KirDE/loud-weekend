# Aggregate product events

Product events are off by default. The client build must opt in via `NEXT_PUBLIC_PRODUCT_EVENTS_ENABLED=true`, and the server must opt in via `PRODUCT_EVENTS_ENABLED=true`. The server flag can stop all product-event writes immediately without a client rebuild. Disabling product events does not disable existing page-view aggregation or retention.

The table has four fields: UTC date, allowlisted event name, UI locale, and count. Search text, applied filter values, festival or artist identifiers, playlist contents, email, account identifiers, IP addresses, cookies and referrers are not attached to the event or persisted by this feature. The browser uses a same-origin request with credentials omitted and no referrer, and skips collection for DNT or GPC. The server also suppresses requests with those signals and rejects non-same-origin browser contexts. The collector accepts small, fixed-schema requests and caps them at 240 attempts per server process per UTC minute, without per-visitor state. Counts represent actions, not distinct people; they are approximate and are not suitable for attribution or billing.

The transport uses the existing page-view path and a separate content type so the exact proxy locations that suppress access logging and client-IP forwarding still apply. Read aggregates with the existing authorized analytics operator request and `kind=product-events`. Both the scheduled endpoint and manual retention script prune counts using the existing configured retention window.

Before enabling outside a disposable environment, confirm effective edge, upstream and application logging redaction on the actual deployment path; document the operator's privacy assessment and disclosure decision alongside the wider privacy work in #430. These implementation properties do not establish a GDPR/ePrivacy conclusion. To roll back, remove the runtime opt-in, then omit the build opt-in on the next build. Leave retention running for previously collected aggregates.
