# Privacy review: application data inventory

This is an engineering inventory for the review in [#430](https://github.com/KirDE/loud-weekend/issues/430), not a public privacy notice. It describes the account-export branch. Compare it with the release commit and deployed configuration before publishing any disclosures. No production configuration or records were inspected for this inventory.

## Application data flows

| Area | Data and behavior in code | Evidence |
| --- | --- | --- |
| Accounts and sign-in | Accounts store email, a password hash for password authentication, and verification state. The session cookie carries an opaque token; the database stores its hash. Sessions stop authenticating after 30 days, and logout deletes the current session. Passkey credentials store public credential material and usage metadata; the five-minute ceremony cookie carries encrypted challenge state. Verification tokens are hashed, expire after 30 minutes and are single-use. | [Authentication](../lib/auth.ts), [passkeys](../lib/passkeys.ts), [email verification](../lib/email-verification.ts), [schema](../prisma/schema.prisma) |
| Planning and sharing | The planner supports browser-local state, explicit account synchronization, and separately created read-only share links. Copies on other devices, downloaded files and recipient copies are not erased by clearing one browser. A share token grants read access to the current synchronized document, including later updates, until the link is removed or expires. | [Account collections](account-collections.md), [share readback](../app/api/share/%5Bslug%5D/route.ts), [schema](../prisma/schema.prisma) |
| Spotify | Connecting starts an OAuth flow with a ten-minute state cookie. The connection stores provider identity and encrypted credentials; the relevant playlist actions can send track selections to Spotify. | [Connect](../app/api/spotify/connect/route.ts), [callback](../app/api/spotify/callback/route.ts), [selection playlist](../app/api/spotify/selection-playlist/route.ts) |
| Notifications and verification email | Preferences select event scope, channel and frequency. Subscriptions can include delivery endpoints and metadata. Delivery records track scheduling, outcomes and diagnostic information. With providers configured, verification email and notifications transmit recipient and message data needed by the selected delivery channel. | [Notification routes](../app/api/notifications), [notification delivery](../lib/notifications.ts), [verification email](../lib/email-verification.ts) |
| Festival submissions and editorial review | The public form stores submitted festival details and optional free text, a reference, deduplication fingerprint and salted digest of a proxy-supplied client address for rate limiting. Editorial work can record actor identity, decisions and evidence. A salted digest is not evidence of anonymous collection. | [Submission route](../app/api/submissions/route.ts), [schema](../prisma/schema.prisma) |
| Browser storage and public caching | Language preference uses local storage with a cookie fallback. The service worker caches eligible public resources and rejects private responses for the public catalog. The account-data export is explicitly not cacheable. | [Language preference](../components/LanguageProvider.tsx), [service worker](../public/sw.js), [export](../app/api/auth/export/route.ts) |
| Analytics | Where configured, the client sends pathname and locale, strips query and fragment, and honors browser DNT/GPC signals. This does not establish how proxies, access logs or a configured endpoint handle network metadata. The aggregate pruning script defaults to 90 days when run; this is not proof of a deployed schedule or policy. | [Client](../lib/privacy-analytics.mjs), [page-view route](../app/api/analytics/page-view/route.ts), [pruning script](../scripts/prune-analytics.mjs) |

The authenticated export provides a session-scoped JSON download of allowlisted product data. It omits authentication secrets, bearer share URLs, provider credentials, push endpoints and internal diagnostics. It does not clear the browser or revoke sessions. Token expiration, disabling a setting, logout and account deletion have different effects; none should be described as equivalent.

## Inputs for operator review

- Confirm the operator/controller identity, published contact details and the channel that handles access, correction and deletion requests.
- Confirm the enabled deployment features, hosting and provider recipients, access and error logs, processing locations and backup behavior. Confirm who controls each external endpoint and which data it receives.
- Approve purposes, legal bases, disclosures and any consent or opt-out behavior against the technologies actually enabled. Review cookie, browser storage and third-party link behavior in the deployed version.
- Specify retention and deletion semantics per data class, including expired tokens, queued and sent deliveries, provider connection revocation, public shares, backups and editorial actor records. Several editorial relations restrict deletion of referenced users; decide which records must remain attributable and how they should be handled before implementing deletion.
- Validate deletion with disposable fixtures: revoke every active session, prevent further queued deliveries, handle linked credentials and public share access, and confirm the agreed handling of retained records. Then verify localized links and disclosures against the same release.
